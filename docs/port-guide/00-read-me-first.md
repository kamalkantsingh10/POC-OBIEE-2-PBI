# Port guide — read me first

The first attempt (POC-RPD) had a Python program that read an OBIEE repository and Web Catalog into a Knowledge Base of CSV tables. It worked well. The Java jar in this project is a port of it. These guides describe that program closely enough to rebuild it without the Python source.

| Guide | Covers |
|---|---|
| `01-repository-reader.md` | Reading the repository (MDS XML): every object type, the 22 repository tables and their columns, expressions, lineage, processing order, errors |
| `02-catalog-reader.md` | Reading the Web Catalog: file layout, dashboards, analyses (reports), columns, views, filters, prompts, saved filters, path resolution, linking report columns to the repository |
| `03-core-output-slice.md` | The "what was not read" audit, the CSV writer, the command line, the slicer, the test rules, and the old as-is skill |

The source-format notes are in `../formats/`. Where a guide and the Architecture Spine disagree, the Architecture Spine wins.

The guides were written on 23 November 2026 by reading the Python code. They were not checked by running it. Each guide marks what its author could not determine.

## The rule for the port

**Port it as it is. Change behaviour only where the old program loses data, corrupts data, or stops the run, and list every such change here.** That way a difference between the new Knowledge Base and the old one is either on this list or a bug.

Notes on how the confirmed differences were built (stories 1.1 and 1.2):

- **3:** the error row has kind `invalid_name`, the object's own source id (or `?`) as `source_id`, the object's type, and the reason the identifier was refused. Only the object or part with the bad name is left out.
- **4:** the error row has kind `unreadable`, the file name as `source_id` and the object-type folder as `object_type`, like `malformed_xml`.
- **5:** each repository reader works in two phases over all files: first it gives every object its identifier, then it produces rows. A physical table's alias link is therefore resolved while the table is read, not in a separate pass.
- **7:** foreign-key columns are already held as Row identifiers in the model (an unresolved one is an empty entry). `physical_joins.csv` itself is written in story 1.6.

Notes on differences 28 to 33:

- **28 to 30, identifiers:** a key's identifier has the fixed word `key` between its owner and its name (`…SAMP_PRODUCTS_D.key.SAMP_PRODUCTS_D_Key`). Without it a key and a column of one name would share an identifier text, as a foreign key and a column already can; in `sampleapp` three tables have a key named `ID` beside a column `ID`.
- **28 to 30, columns that do not resolve:** as for a foreign key's own columns (difference 7), an entry that does not resolve is an empty line and no error row is written.
- **28, primary key:** the word "primary" is not used for a physical key anywhere in the Knowledge Base or the packets. The packet says "the repository does not say whether a physical key is the primary key", how many keys the table has, and how many foreign keys of the slice point at exactly the key's columns.

## Kept as it is, though it is a known limit

- `lts_column_map` and `lineage` record only the first database column of a mapping that uses several.
- Different kinds of object can produce the same identifier text; duplicates are reported in `errors.csv`.
- Prompts saved as separate view objects, Visual Analyzer projects, scorecards, KPIs, actions and agents are counted and not read.
- Linking report columns to the repository has only ever succeeded on small hand-made estates (the first attempt's pair and this project's `src/test/fixtures/linked-estate`), because the public sample repository and catalog come from different systems.
- Only a report formula that is nothing but `"Table"."Column"` is linked. The columns inside a calculation are not looked for.
- When two presentation columns of one subject area differ only in letter case and a report names neither exactly, the one read last from the repository is taken, with no warning. The same holds for two subject areas that differ only in case. (The catalog's path resolution, by contrast, reports such a case as `ambiguous`.) Not seen in the samples.

## Care needed in Java

- **Sorting and rounding.** To match the old output byte for byte, sort by Unicode code point (Java's default string order differs for rare characters) and round percentages half-to-even.
- **Element text.** The old program's idea of an element's text is not what Java's DOM `getTextContent()` returns. Guide 02 gives the rule.
- **The audit.** Every read of the XML must go through the recording layer, or gaps go unreported with no visible sign. Guide 03 recommends building a small tree of our own from the JDK's streaming reader.
- **Namespace declarations** must not be counted as unread attributes.

Notes added in stories 1.8 and 1.9 (reports, columns, views, filters, prompts, saved filters):

- **8, rule for formulas (`analysis_columns.formula`, `analysis_prompts.column_formula`): the whole text.** All the character data inside the expression element, in document order: its own text, the text of every element nested in it at any depth, and the text between and after them. Comments and processing instructions are not text. Tags and attributes of nested elements are not part of it, so nested parts follow on with nothing in between: `CAST(<sawx:expr xsi:type="sawx:eval">EVALUATE(1)</sawx:expr>)` is stored as `CAST(EVALUATE(1))`. Nothing is trimmed. It is `XmlNode.deepText()`, the same thing as the DOM's text content. These nested parts have no rows of their own, so this is the only place they are kept.
- **8, rule for filters (`analysis_filters.expr_text` in every scope, `saved_filters.expr_text`): the own text.** All the character data directly inside the expression element, before, between and after its children, plus the whole text of nested elements that are **not** `sawx:expr` (they get no row). The text of a nested `sawx:expr`, and of anything inside it, is **not** included: it is in that expression's own row. Text after a nested expression is kept. Nothing is trimmed. It is `XmlNode.ownText("…expr")`: the whole text with every nested expression cut out. So `CAST(<sawx:expr …>EVALUATE(1)</sawx:expr> AS INT)` in a filter gives two rows, `CAST( AS INT)` and `EVALUATE(1)`; a leaf row is its column, formula or literal; a group or comparison row holds only what is written directly in it, usually white space or nothing. (As first built, a filter row held the whole text, which put every operand of a group, run together, in the group's row; narrowed at the coordinator's request.) Headings are the text of a `saw:text` element and are unchanged.
- **8, on the sample catalog.** No expression in `sampleapp-v607` has text of its own before a nested element (the `CAST(` shape occurs only in the test fixtures). Formulas: 15 `analysis_columns.formula` cells change, all of type `sawx:binned` (the base formula and the bin rules, which the old program captured nowhere; the reference held nothing or white space). Filters: 440 of the 7,135 shared `analysis_filters.expr_text` cells and 3 of the 96 `saved_filters.expr_text` cells change, and every one only gains white space: the line breaks and tabs the source has between and after an expression's children, where the old program stopped at the first child. The other 6,695 and 93 are equal to the reference.
- **8 and the audit.** Text taken as part of a stored text is no longer listed as unread text (`unparsed.csv`, `...expr#text` for reports: 4,426 in the reference, 4,269 now). A nested element is **not** thereby counted as read: unless a reader reads it in its own right it is still listed as an unread element, and its attributes as unread attributes. So `unread_element` and `unread_attribute` rows are as in the reference.
- **9, where a saved filter's conditions are written.** As ordinary `analysis_filters` rows with `scope` = `saved_filter` and `owner_id` = the saved filter, one row per `sawx:expr` below the object's direct `saw:filter` elements, in document order, with Row identifier `<saved filter path>#f<k>` (no criteria number, which is what tells it from a report's `#f<i>.<k>`). `saved_filters` keeps one row per object. Its `op` and `expr_type` are the outermost expression's, as in the old program; its `expr_text` is that expression's own text (difference 8, the rule for filters) and equals `expr_text` of the `#f0` row.
- **9, references between saved filters.** A saved filter that refers to another by path is now resolved, like the same reference inside a report (the old program never reached these, because it read only the outermost expression). One that does not resolve gets an `errors.csv` row whose `source_id` is the saved filter's path. On the sample: 76 such references, 57 resolved, 19 error rows, and `coverage.skipped` for `...expression/v1.1}expr` goes from 176 to 195.
- **9 and the audit.** The operator, path and text of a saved filter's nested expressions are read now, so the three `unparsed.csv` rows that listed them for saved filters (564, 76 and 579 occurrences) are gone.
- **10.** `analysis_filters` has two more columns, at the end: `parent_id` (the row of the nearest enclosing `sawx:expr` below the same `saw:filter`; empty for the outermost) and `depth` (how many such expressions enclose it; 0 for the outermost). Elements between two expressions that are not expressions (`saw:columnFormula` inside a `sawx:columnExpression`) are passed over. Row identifiers, positions and row order are as in the old program. Dashboard-scope rows have no parent and depth 0.
- **11.** The dashboard-scope rows are written by `DashboardPageReader` in the same loop as the placements, from the outcome it has just obtained. Nothing resolves a global filter view a second time.
- **Kept as it is:** a column outside every criteria block is not captured; only the first formula of a column is stored; `is_computation` comes from the column element's type; an untyped `saw:prompt` is skipped and uses up a number; if a criteria block sits inside a filter, its filter expressions are written twice, once under each block (guide 02 §7.3; not seen in the sample). - **The audit is the reference's, read for read.** The check for a database function stops at the first one it finds, as the Python's `any()` does, because every expression it asks counts as looked at. With that, every `unparsed` row for reports and saved filters equals the reference's apart from the rows named above.

Holding every report's tree until a final audit needed a 256 MB heap on the sample; this way it runs in 96 MB again, with the same bytes written. The path index is built from file names before the first object is read, and no row depends on another object having been read first.

Notes added after the first real run of the skills on Sample Sales (23 November 2026):

- **26, how the source stores it.** A `PhysicalForeignKey` is a child of its `PhysicalTable`. Its `counterPartKeyRef` attribute points, by `mdsid`, at a `PhysicalKey` element, which is a child of the table it is a key of. Both elements list their columns the same way: `RefColumns/RefColumn@columnRef`. So the far table is the element that encloses the key, and the far columns are the key's `RefColumn` entries in source order. OBIEE pairs the two lists by position; the jar does not check that they have the same length (on the samples they always do) and a packet states pairs only when they do.
- **26 and the audit.** Only what reaches a table counts as read: the foreign key's link, the key element that is followed, its column list and the column references in it. `PhysicalKey@name` and `PhysicalKey@mdsid` stay listed for every key, because no table carries them.
- **26 and the slicer.** The reference rule for physical joins is "both ends in the slice". Now that a foreign key has a far end, the rule applies to it too: a foreign key that points at a table outside the slice is not in the slice. On Sample Sales all 14 foreign keys stay (every far table is a table of the slice). The columns at both ends of a kept join are part of the walk.
- **27 and the audit.** `Group@displayName` and `Group@guid` are read only for a role that a privilege package with at least one query privilege points at, because only then is there a row to carry them.
- **Comparing.** `KbCompare` recognises 26 and 27 by reading the estate's repository files itself, with the JDK's streaming parser. 26: the far table and the far columns are built again from the names in the files for every foreign key; the `unparsed` counts must fall by exactly the number of links, followed keys, their column lists and the column references in them. 27: the two added cells of every `query_privilege` row must be what the file of the package's role holds; the `unparsed` counts must fall by exactly the number of roles pointed at that have the attribute. Without the estate folder both stay unexplained.
- **13, variables, widened.** A variable is still matched by its whole name. When no variable has exactly the name an expression writes, one whose name differs only in letter case is taken (OBIEE does not tell variable names apart by letter case; `bi-analytics-2013` has `VALUEOF(Anton_tserakhau_v_cur_month)` for the variable `Anton_Tserakhau_v_cur_month`), and the `variables` packet says that the letter case differs. A name that no variable has brings nothing into the slice; the packet lists it, with the rows that use it, as "used by name, not defined in the repository" (on Sample Sales: `WEBLANGUAGE`, seven `CN_Sample_Sales_Dim_Time…` names in display-name formulas, and `PREFERED_CURRENCY`, which an init block's query writes with one R). The forms read are those the samples hold: `VALUEOF` and `NQ_SESSION` in any letter case, white space inside the brackets and around the dot, a name in double quotes, and a number and comma before the name (`valueof(0,NQ_SESSION.LEDGER)`). `%1`, `%2` … inside `VALUEOF` is a placeholder of a formula template, not a name.
- **24, packets.** A packet has at most `--max-packet-lines` lines (default 120; the first cut used a fixed 400). A logical table is laid out as what it offers (columns) and then where its data comes from (one table source after the other, each with its mappings and lineage), and is cut there first, then between items.
